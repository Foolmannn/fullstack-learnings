# Data Fetching in Next.js — Detailed Guide

Data fetching is one of the most important parts of Next.js because Next.js supports **Server Components, Client Components, Server Actions, Route Handlers, caching, revalidation, and streaming**.

If you already know React, the biggest conceptual shift is:

> **In traditional React, you often fetch data in the browser with `useEffect()`. In modern Next.js, you can fetch data directly on the server and send the rendered result to the client.**

I'll explain this from basic → intermediate → advanced.

---

# 1. What is Data Fetching?

Suppose your backend has:

```text
GET https://api.example.com/products
```

and returns:

```json
[
  {
    "id": 1,
    "name": "Laptop",
    "price": 800
  },
  {
    "id": 2,
    "name": "Phone",
    "price": 500
  }
]
```

Your Next.js application needs to:

1. Request the data
2. Receive the response
3. Convert it to JavaScript data
4. Render it in the UI

There are several places where this fetching can happen.

### Main approaches

| Approach                   | Runs where?   | Typical use                                    |
| -------------------------- | ------------- | ---------------------------------------------- |
| Server Component `fetch()` | Server        | Pages/data that don't need browser interaction |
| Client `fetch()`           | Browser       | Interactive/live client-side data              |
| Server Action              | Server        | Mutations/forms                                |
| Route Handler              | Server        | Creating your own API endpoint                 |
| Database query             | Server        | Direct database access                         |
| Third-party library        | Client/Server | Complex client-side fetching                   |

---

# 2. React vs Next.js Data Fetching

In a normal React application, you might write:

```jsx
"use client";

import { useEffect, useState } from "react";

export default function Products() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    fetch("/api/products")
      .then(res => res.json())
      .then(data => setProducts(data));
  }, []);

  return (
    <div>
      {products.map(product => (
        <p key={product.id}>{product.name}</p>
      ))}
    </div>
  );
}
```

The sequence is:

```text
Browser
   ↓
Render React page
   ↓
useEffect()
   ↓
API request
   ↓
Server
   ↓
Data
   ↓
setState()
   ↓
Re-render
```

This means the user may initially see:

```text
Loading...
```

Then the data appears.

---

# 3. Next.js Server Component Fetching

With the App Router, you can fetch directly inside a Server Component.

For example:

```jsx
export default async function Products() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  const products = await response.json();

  return (
    <div>
      {products.map(product => (
        <p key={product.id}>
          {product.name}
        </p>
      ))}
    </div>
  );
}
```

Notice something important:

```jsx
export default async function Products()
```

The component itself is `async`.

You can therefore use:

```jsx
await fetch(...)
```

directly.

---

# 4. Why Can Next.js Do This?

Because the component is running on the **server**.

The browser doesn't execute this:

```jsx
const response = await fetch("https://api.example.com/products");
```

Instead:

```text
                    Next.js Server
                         │
                         │ fetch()
                         ↓
                 External API
                         │
                         ↓
                       Data
                         │
                         ↓
                 React rendering
                         │
                         ↓
                     Browser
```

This has several benefits.

### Benefit 1 — Less client-side JavaScript

You don't necessarily need:

```jsx
useEffect
useState
```

for simple server-rendered data.

### Benefit 2 — Secrets stay on server

Suppose your API requires:

```env
API_SECRET=abc123
```

You don't want this secret sent to the browser.

Server-side fetching allows:

```js
const response = await fetch(
  "https://api.example.com/data",
  {
    headers: {
      Authorization: `Bearer ${process.env.API_SECRET}`
    }
  }
);
```

The secret remains on the server.

---

# 5. Server Components vs Client Components

This distinction is extremely important.

## Server Component

By default, files in the App Router are Server Components.

```jsx
export default async function Page() {
  const response = await fetch("https://api.example.com/users");

  const users = await response.json();

  return <div>...</div>;
}
```

You can:

* fetch data
* access databases
* access environment variables
* perform server-side operations

But you cannot use browser-only React features such as:

```jsx
useState()
useEffect()
```

---

# 6. Client Component

If you write:

```jsx
"use client";
```

the component becomes a Client Component.

Example:

```jsx
"use client";

import { useEffect, useState } from "react";

export default function Products() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    fetch("/api/products")
      .then(res => res.json())
      .then(data => setProducts(data));
  }, []);

  return <div>...</div>;
}
```

Now fetching happens in the browser.

---

# 7. When Should You Use Server Fetching?

Prefer server fetching when the data:

* doesn't require browser interaction
* is needed to render the page
* comes from a database/backend
* requires secret credentials
* can be fetched before rendering

For example:

```text
Product page
Blog page
User profile
Dashboard statistics
News page
Documentation page
```

---

# 8. When Should You Use Client Fetching?

Client-side fetching makes sense when the data depends heavily on browser interaction.

For example:

```text
Search suggestions
Live notifications
Infinite scrolling
Client-side filters
Real-time dashboards
Chat applications
Auto-refreshing data
```

Example:

```jsx
"use client";

import { useEffect, useState } from "react";

export default function Notifications() {
  const [notifications, setNotifications] = useState([]);

  useEffect(() => {
    async function loadNotifications() {
      const response = await fetch("/api/notifications");
      const data = await response.json();

      setNotifications(data);
    }

    loadNotifications();
  }, []);

  return (
    <div>
      {notifications.map(notification => (
        <p key={notification.id}>
          {notification.message}
        </p>
      ))}
    </div>
  );
}
```

# 10. Fetching Directly From a Database

One of the powerful things about Server Components is that you don't necessarily need to create an API endpoint just for your own frontend.

For example:

```text
Next.js Server Component
        ↓
PostgreSQL
```

You could have:

```js
import { db } from "@/lib/db";

export default async function UsersPage() {
  const users = await db.user.findMany();

  return (
    <div>
      {users.map(user => (
        <p key={user.id}>{user.name}</p>
      ))}
    </div>
  );
}
```

This is often preferable to:

```text
Next.js
 ↓
/api/users
 ↓
Database
```

when the API isn't needed by another client.

# 11. Error Handling

Never assume that `fetch()` automatically throws an error for HTTP errors.

For example:

```text
404
500
401
```

may still produce a Response object.

So you should check:

```jsx
export default async function Products() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  if (!response.ok) {
    throw new Error("Failed to fetch products");
  }

  const products = await response.json();

  return (
    <div>
      {products.map(product => (
        <p key={product.id}>{product.name}</p>
      ))}
    </div>
  );
}
```

# 14. Dynamic Data

Suppose you have:

```text
/products/1
/products/2
/products/3
```

Your folder could be:

```text
app/
└── products/
    └── [id]/
        └── page.jsx
```

Then:

```jsx
export default async function ProductPage({ params }) {
  const { id } = await params;

  const response = await fetch(
    `https://api.example.com/products/${id}`
  );

  const product = await response.json();

  return (
    <div>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
    </div>
  );
}
```

The URL:

```text
/products/5
```

gives:

```js
id = "5"
```

```jsx
export default async function ProductsPage({ searchParams }) {

  const response = await fetch(

  const products = await response.json();

  return (
    <div>
      ...
    </div>
  );
}
```

So:

```text
/products?category=laptop
```

gives:

```js
category = "laptop"
```

# 16. Caching

This is where Next.js data fetching becomes more interesting.

Imagine:

```jsx
const response = await fetch(
  "https://api.example.com/products"
);
```

Next.js can control how that request is cached/revalidated depending on the configuration and current Next.js behavior.

You should understand these concepts:

```text
Cache
Revalidation
Dynamic rendering
Static rendering
```

---

# 17. Revalidation

Suppose your product data changes occasionally.

You don't want to request the API every single time.

You can specify a revalidation period.

Conceptually:

```jsx
const response = await fetch(
  "https://api.example.com/products",
  {
    next: {
      revalidate: 60
    }
  }
);
```

This means the fetched result can be revalidated approximately every:

```text
60 seconds
```

This approach is useful for:

```text
Blogs
Products
News
Documentation
Public profiles
```

where data changes periodically rather than every second.

---

# 18. No-Cache / Always Fresh Data

For data that must always be fresh, you can opt out of caching.

```jsx
const response = await fetch(
  "https://api.example.com/orders",
  {
    cache: "no-store"
  }
);
```

Useful for things like:

```text
Bank balance
Current account information
Live order status
Frequently changing dashboard data
```

---

# 19. Static vs Dynamic Rendering

Think of two pages.

### Page A

```text
Blog article
```

The content changes once every few hours.

You can use:

```text
Static rendering
+
Revalidation
```

### Page B

```text
User's current account balance
```

You probably want:

```text
Dynamic rendering
```

because the data is user-specific and potentially changes frequently.

# 20. Parallel Data Fetching

Suppose your dashboard requires:

```text
User
Expenses
Income
Notifications
```

You shouldn't necessarily do:

```jsx
const user = await getUser();

const expenses = await getExpenses();

const income = await getIncome();

const notifications = await getNotifications();
```

This can create a waterfall:

```text
User
 ↓
Expenses
 ↓
Income
 ↓
Notifications
```

Instead, if they're independent:

```jsx
const userPromise = getUser();
const expensesPromise = getExpenses();
const incomePromise = getIncome();
const notificationsPromise = getNotifications();

const [
  user,
  expenses,
  income,
  notifications
] = await Promise.all([
  userPromise,
  expensesPromise,
  incomePromise,
  notificationsPromise
]);
```

Now they can execute concurrently:

```text
       ┌── User
       ├── Expenses
Start ─┼── Income
       └── Notifications
```

This can significantly improve performance.

---

# 21. Sequential Data Fetching

Sometimes you actually need sequential fetching.

Example:

```text
Get user
   ↓
Get user's ID
   ↓
Get user's orders
```

Then:

```jsx
const user = await getUser();

const orders = await getOrders(user.id);
```

Here the second request depends on the first.

So sequential fetching is appropriate.

---

# 22. Waterfalls

A waterfall happens when:

```text
Request A
   ↓
Request B
   ↓
Request C
```

instead of:

```text
Request A ──┐
Request B ──┼──→ Results
Request C ──┘
```

Avoid unnecessary waterfalls because they increase total waiting time.

# 23. Fetching Data in Components

You don't necessarily have to fetch everything in `page.jsx`.

You can have:

```text
app/
└── dashboard/
    ├── page.jsx
    ├── UserInfo.jsx
    ├── Expenses.jsx
    └── Income.jsx
```

For example:

```jsx
async function Expenses() {
  const response = await fetch(
    "https://api.example.com/expenses"
  );

  const expenses = await response.json();

  return (
    <div>
      {expenses.map(expense => (
        <p key={expense.id}>
          {expense.amount}
        </p>
      ))}
    </div>
  );
}
```

Then:

```jsx
export default function Dashboard() {
  return (
    <div>
      <UserInfo />
      <Expenses />
      <Income />
    </div>
  );
}
```

This component-based approach can work very well with streaming and Suspense.

# 24. Streaming

One of the major advantages of the App Router is streaming.

Imagine:

```text
Dashboard

User information       ███████
Expenses               █████████████
Income                 ████
Analytics              ████████████████
```

Instead of waiting for everything:

```text
Wait for EVERYTHING
       ↓
Render page
```

Next.js can progressively send parts of the UI.

Conceptually:

```text
Page shell
   ↓
User information
   ↓
Income
   ↓
Expenses
   ↓
Analytics
```

This makes large applications feel faster.

# 25. Suspense

You can use React's `Suspense`.

```jsx
import { Suspense } from "react";

export default function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>

      <Suspense fallback={<p>Loading expenses...</p>}>
        <Expenses />
      </Suspense>
    </div>
  );
}
```

Then:

```jsx
async function Expenses() {
  const response = await fetch(
    "https://api.example.com/expenses"
  );

  const expenses = await response.json();

  return (
    <div>
      {expenses.map(expense => (
        <p key={expense.id}>
          {expense.amount}
        </p>
      ))}
    </div>
  );
}
```

Now the page doesn't necessarily have to wait for `Expenses` before rendering the rest of the UI.

# 26. Server Actions

Server Actions are particularly useful for **mutations**.

Fetching:

```text
GET
```

is generally about reading.

Mutations:

```text
POST
PUT
PATCH
DELETE
```

change data.

For example:

```text
Add Expense
```

in your MeroHisab-style application.

You might have:

```text
Client
  ↓
Server Action
  ↓
Database
```

instead of:

```text
Client
  ↓
API endpoint
  ↓
Server
  ↓
Database
```

A simplified Server Action looks like:

```jsx
"use server";

export async function addExpense(formData) {
  const title = formData.get("title");
  const amount = formData.get("amount");

  await db.expense.create({
    data: {
      title,
      amount: Number(amount)
    }
  });
}
```

Then a form can invoke that action.

# 27. Route Handlers

Next.js can also create API endpoints.

For example:

```text
app/
└── api/
    └── products/
        └── route.js
```

You can write:

```js
export async function GET() {
  const products = await db.product.findMany();

  return Response.json(products);
}
```

Then:

```text
GET /api/products
```

returns the products.

# 28. Route Handler vs Server Component

This distinction is important.

### Server Component

Use when:

```text
Next.js UI
   ↓
Data
```

For example:

```jsx
const products = await db.product.findMany();
```

### Route Handler

Use when:

```text
External client
      ↓
Next.js API
      ↓
Database
```

For example:

```text
Mobile app
React app
Third-party client
Postman
External service
       ↓
/api/products
```

Route Handlers are essentially your API layer.

# 29. Environment Variables

Suppose:

```env
DATABASE_URL="..."
API_SECRET="..."
```

Don't expose secrets to the browser.

Server code:

```js
const response = await fetch(API_URL, {
  headers: {
    Authorization: `Bearer ${process.env.API_SECRET}`
  }
});
```

is safe from the perspective of keeping the secret server-side.

But variables prefixed with:

```text
NEXT_PUBLIC_
```

are intended to be exposed to client-side code.

For example:

```env
NEXT_PUBLIC_API_URL="..."
```

should be treated as public.

Suppose the user is logged in.

You might have:

```text
Browser
   ↓
Next.js Server
   ↓
Authentication
   ↓
Database
```

The server can identify the user and fetch:

```jsx
const user = await getCurrentUser();

    userId: user.id
```

This is often much cleaner than sending sensitive authentication information from a client component.

# 32. Data Layer

For larger applications, don't put all database logic directly into components.

Instead:

```text
app/
│
├── dashboard/
│   └── page.jsx
│
lib/
│
├── db.js
├── users.js
├── expenses.js
└── income.js
```

For example:

```js
// lib/expenses.js

export async function getRecentExpenses(userId) {
  return db.expense.findMany({
    where: {
      userId
    },
    orderBy: {
      createdAt: "desc"
    },
    take: 10
  });
}
```

Then:

```jsx
import { getRecentExpenses } from "@/lib/expenses";

export default async function Dashboard() {
  const expenses = await getRecentExpenses(userId);

  return <Expenses data={expenses} />;
}
```

This separates:

```text
UI
 ↓
Data functions
 ↓
Database
```

which is much easier to maintain.

# 33. Common Mistake — Using `useEffect` Everywhere

If you're coming from React, you may naturally do:

```jsx
"use client";

useEffect(() => {
  fetch(...);
}, []);
```

for everything.

That's not necessarily the best approach in Next.js.

Ask:

> **Does this data actually need to be fetched in the browser?**

If not, consider:

```jsx
async function ServerComponent() {
  const data = await fetch(...);

  return ...
}
```

---

# 34. Common Mistake — Making Everything Client Components

Avoid putting:

```jsx
"use client";
```

at the top of every component.

You lose some of the advantages of Server Components.

Instead, try to keep the server/client boundary as small as practical.

For example:

```text
Dashboard (Server)
│
├── Summary (Server)
│
├── ExpenseList (Server)
│
└── ExpenseChart (Client)
```

The chart may need:

```jsx
"use client";
```

because it uses browser-side interaction.

But the database fetching can remain server-side.

---

# 35. Recommended Architecture

For a modern Next.js application:

```text
                    Browser
                       │
                       ↓
                Client Components
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
       Server Actions      Route Handlers
             │                   │
             └─────────┬─────────┘
                       ↓
                  Data Layer
                       ↓
                   Database
```

For simple page reads:

```text
Server Component
      ↓
Data Layer
      ↓
Database
```

is often enough.

# 36. The Most Important Mental Model

Think about Next.js data fetching in **three categories**.

### READ

```text
Where does data come from?
```

Usually:

```text
Server Component
      ↓
Database/API
```

### INTERACTIVE READ

```text
Does the browser need to control the request?
```

Then:

```text
Client Component
      ↓
fetch / React Query / SWR
```

### WRITE / MUTATION

```text
Does the user modify data?
```

Then consider:

```text
Form
 ↓
Server Action
 ↓
Database
```

or:

```text
Client
 ↓
Route Handler
 ↓
Database
```

# 37. A Practical Decision Tree

When you need data in Next.js, ask:

```text
                 Need data?
                     │
                     ↓
          Is it needed for rendering?
                /          \
              Yes           No
               │             │
               ↓             ↓
         Server-side     Client-side
               │
               ↓
     Does browser interaction
          control it?
          /       \
        No         Yes
        │           │
        ↓           ↓
 Server Component  Client Component
        │
        ↓
 Database/API
```

For mutations:

```text
User submits form
       ↓
Does it modify server data?
       ↓
    Server Action
       ↓
    Database
```
