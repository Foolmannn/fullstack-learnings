# Error Handling and Error Recovery in Next.js

In modern **Next.js App Router**, error handling is mainly done using special files such as:

* `error.tsx` → handles **runtime errors in a route segment**
* `global-error.tsx` → handles errors in the **root layout**
* `not-found.tsx` → handles **404 / resource-not-found situations**
* `loading.tsx` → handles **loading states**, not errors
* `redirect()` → handles intentional navigation, not errors
* `try/catch` → handles errors locally when you want custom recovery logic

The important idea is:

> **Error handling** = detecting and displaying an error safely.
> **Error recovery** = giving the user a way to retry, navigate somewhere safe, or recover without restarting the entire application.

---

# 1. Why Error Handling Is Important

Imagine this page:

```text
/products
```

It fetches products from an API:

```tsx
async function ProductsPage() {
  const response = await fetch("https://api.example.com/products");

  if (!response.ok) {
    throw new Error("Failed to fetch products");
  }

  const products = await response.json();

  return <ProductList products={products} />;
}
```

What happens if the API is down?

Without proper error handling, the user may get an ugly error page.

Instead, we can create:

```text
app/
├── products/
│   ├── page.tsx
│   └── error.tsx
```

and Next.js can display the error UI for that route.

---

# 2. `error.tsx`

The most important mechanism for error handling in the App Router is:

```text
error.tsx
```

For example:

```text
app/
├── page.tsx
├── products/
│   ├── page.tsx
│   └── error.tsx
```

`products/error.tsx` handles errors occurring within the `products` route segment.

---

## Basic Example

### `app/products/page.tsx`

```tsx
export default async function ProductsPage() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  if (!response.ok) {
    throw new Error("Failed to fetch products");
  }

  const products = await response.json();

  return (
    <div>
      <h1>Products</h1>

      {products.map((product: any) => (
        <div key={product.id}>
          {product.name}
        </div>
      ))}
    </div>
  );
}
```

If the request fails:

```tsx
throw new Error("Failed to fetch products");
```

Next.js looks for the nearest `error.tsx`.

---

# 3. Creating `error.tsx`

```tsx
"use client";

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>

      <button onClick={() => reset()}>
        Try again
      </button>
    </div>
  );
}
```

Notice two important things:

```tsx
error
```

and:

```tsx
reset
```

---

# 4. What Is `error`?

The `error` object contains information about the error.

For example:

```tsx
error.message
```

could contain:

```text
Failed to fetch products
```

You could display it:

```tsx
<p>{error.message}</p>
```

However, **don't blindly expose internal/server error details to users**, especially in production.

A better UI is often:

```tsx
<h2>Unable to load products</h2>
<p>Please try again.</p>
```

while logging the actual error separately.

---

# 5. What Is `reset()`?

This is where **error recovery** comes in.

```tsx
<button onClick={() => reset()}>
  Try again
</button>
```

`reset()` tells Next.js:

> Try rendering this route segment again.

So the flow becomes:

```text
Request
   ↓
Page throws error
   ↓
error.tsx appears
   ↓
User clicks "Try again"
   ↓
reset()
   ↓
Next.js attempts rendering again
```

This is one of the simplest forms of **error recovery**.

---

# 6. Why Does `error.tsx` Need `"use client"`?

`error.tsx` is a **Client Component**.

Why?

Because it usually contains interactive behavior:

```tsx
<button onClick={reset}>
```

Event handlers such as:

```tsx
onClick
```

require Client Components.

Therefore:

```tsx
"use client";
```

is required.

---

# 7. Error Boundaries

Under the hood, `error.tsx` works as an **error boundary** for its route segment.

Consider:

```text
app/
├── layout.tsx
├── page.tsx
│
├── dashboard/
│   ├── layout.tsx
│   ├── page.tsx
│   └── error.tsx
│
└── settings/
    ├── page.tsx
    └── error.tsx
```

If something fails inside:

```text
/dashboard
```

Next.js can show:

```text
dashboard/error.tsx
```

without necessarily replacing the entire application.

Conceptually:

```text
Root Layout
│
├── Dashboard
│   ├── Page ← ERROR
│   └── error.tsx ← catches it
│
└── Other UI
```

This is useful because the surrounding UI can remain intact.

---

# 8. Nested Error Boundaries

One of the powerful features of Next.js is that error boundaries can be nested.

Example:

```text
app/
│
├── error.tsx
│
├── dashboard/
│   ├── error.tsx
│   │
│   ├── analytics/
│   │   ├── error.tsx
│   │   └── page.tsx
│   │
│   └── page.tsx
```

Suppose:

```text
/dashboard/analytics
```

throws an error.

Next.js first looks for the closest error boundary:

```text
analytics/error.tsx
```

If that boundary is not available, it can bubble up to:

```text
dashboard/error.tsx
```

and then potentially:

```text
app/error.tsx
```

This gives you granular error handling.

---

# 9. Important: `error.tsx` Doesn't Catch Everything

A common misunderstanding is:

> "`error.tsx` catches every possible error."

Not exactly.

There are different types of errors.

For example:

```text
Rendering errors
Data fetching errors
Client-side errors
404 errors
Root layout errors
Build-time errors
```

Different mechanisms may be appropriate for each.

---

# 10. Handling `not-found`

Suppose the user visits:

```text
/products/999999
```

but product `999999` doesn't exist.

This isn't necessarily a server failure.

It's a **not found** situation.

Next.js provides:

```text
not-found.tsx
```

Example:

```text
app/
└── products/
    ├── [id]/
    │   ├── page.tsx
    │   └── not-found.tsx
```

---

## `page.tsx`

```tsx
import { notFound } from "next/navigation";

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

  const product = await getProduct(id);

  if (!product) {
    notFound();
  }

  return (
    <div>
      <h1>{product.name}</h1>
    </div>
  );
}
```

Then:

```text
app/products/[id]/not-found.tsx
```

could contain:

```tsx
export default function NotFound() {
  return (
    <div>
      <h1>Product Not Found</h1>
      <p>The product you're looking for doesn't exist.</p>
    </div>
  );
}
```

---

# 11. `error.tsx` vs `not-found.tsx`

This distinction is extremely important.

### `error.tsx`

Use when something **unexpected went wrong**.

Example:

```text
Database connection failed
API failed
Unexpected exception
Rendering error
```

### `not-found.tsx`

Use when something **doesn't exist**.

Example:

```text
Product doesn't exist
Blog post doesn't exist
User doesn't exist
```

Think:

```text
Something went wrong
       ↓
    error.tsx
```

versus:

```text
Requested resource doesn't exist
       ↓
    not-found.tsx
```

---

# 12. `global-error.tsx`

There's another special file:

```text
global-error.tsx
```

This is used for errors that affect the **root layout**.

Example:

```text
app/
├── layout.tsx
├── global-error.tsx
```

Normally, `error.tsx` itself depends on a layout being able to render.

But if the root layout itself crashes, you need a higher-level fallback.

Example:

```tsx
"use client";

export default function GlobalError({
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <html>
      <body>
        <h1>Something went wrong</h1>

        <button onClick={() => reset()}>
          Try again
        </button>
      </body>
    </html>
  );
}
```

`global-error.tsx` must provide its own:

```html
<html>
  <body>
```

because it replaces the root layout when active.

---

# 13. `try/catch` in Next.js

You can also handle errors manually.

For example:

```tsx
async function getProducts() {
  try {
    const response = await fetch(
      "https://api.example.com/products"
    );

    if (!response.ok) {
      throw new Error("Failed to fetch products");
    }

    return await response.json();

  } catch (error) {
    console.error(error);

    return [];
  }
}
```

Then:

```tsx
export default async function ProductsPage() {
  const products = await getProducts();

  return (
    <div>
      {products.map((product: any) => (
        <p key={product.id}>
          {product.name}
        </p>
      ))}
    </div>
  );
}
```

Here, the error doesn't reach `error.tsx`.

Why?

Because you caught it:

```tsx
catch (error) {
  return [];
}
```

---

# 14. `try/catch` vs `error.tsx`

This is a very important design decision.

### Use `try/catch` when:

You can **meaningfully recover locally**.

For example:

```text
API fails
   ↓
Show cached data
```

or:

```text
Optional recommendation API fails
   ↓
Continue without recommendations
```

### Use `error.tsx` when:

The error is serious enough that the route segment cannot render normally.

For example:

```text
Database request failed
       ↓
Page cannot render
       ↓
throw error
       ↓
error.tsx
```

# 15. Error Recovery Example

Imagine:

```tsx
async function ProductsPage() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  if (!response.ok) {
    throw new Error("Failed to load products");
  }

  const products = await response.json();

  return <ProductList products={products} />;
}
```

And:

```tsx
"use client";

export default function Error({
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Unable to load products.</h2>

      <button onClick={reset}>
        Try Again
      </button>
    </div>
  );
}
```

The recovery mechanism is:

```text
              Products Page
                    │
                    ▼
              Fetch products
                    │
             ┌──────┴──────┐
             │             │
           success        failure
             │             │
             ▼             ▼
        Show products   error.tsx
                           │
                           ▼
                       Try Again
                           │
                           ▼
                         reset()
                           │
                           ▼
                     Fetch again
```

# 16. Recovering From Client-Side Errors

Suppose you have:

```tsx
"use client";

export default function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    // some code that may throw
  }

  return (
    <button onClick={handleClick}>
      {count}
    </button>
  );
}
```

Client-side runtime errors can also be caught by the appropriate error boundary.

For more specialized client-side error handling, React's error-boundary model is important.

The key concept is:

```text
Component
   ↓
throws error
   ↓
nearest Error Boundary
   ↓
fallback UI
```

In Next.js App Router, `error.tsx` gives you this route-level mechanism.

---

# 17. Logging Errors

You should generally **log the actual error** while showing the user a friendly message.

For example:

```tsx
"use client";

import { useEffect } from "react";

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    console.error(error);
  }, [error]);

  return (
    <div>
      <h2>Something went wrong.</h2>

      <button onClick={reset}>
        Try again
      </button>
    </div>
  );
}
```

In production, you would typically send errors to an observability/error-tracking system rather than relying only on `console.error`.

---

# 18. Error Digest

You may see:

```tsx
error.digest
```

The error object can include a `digest` value.

Example:

```tsx
console.log(error.digest);
```

A digest can help identify an error associated with a server-side failure without exposing sensitive server details to the browser.

You generally shouldn't build your UI around exposing the digest itself.

---

# 19. Server Actions and Error Handling

This becomes especially important with forms.

Suppose:

```tsx
"use server";

export async function createUser(formData: FormData) {
  const name = formData.get("name");

  // database operation
}
```

You shouldn't necessarily throw an exception for every expected user mistake.

For example:

```text
Email already exists
Invalid username
Password doesn't meet requirements
```

These are often **expected application errors**, not unexpected crashes.

A better pattern is to return structured state:

```tsx
"use server";

export async function createUser(
  previousState: any,
  formData: FormData
) {
  const name = formData.get("name");

  if (!name) {
    return {
      error: "Name is required",
    };
  }

  // create user...

  return {
    success: true,
  };
}
```

Then the UI can display:

```text
Name is required
```

without triggering a full error boundary.

---

# 20. Expected vs Unexpected Errors

This distinction is extremely useful.

## Expected error

Something the application knows can happen.

Examples:

```text
Invalid form input
Wrong password
Email already registered
Product not available
Unauthorized action
```

Handle these explicitly.

For example:

```tsx
return {
  error: "Email already exists"
};
```

---

## Unexpected error

Something that shouldn't normally happen.

Examples:

```text
Database crashes
Unexpected exception
Bug in application
External service failure
Programming error
```

These can be allowed to propagate:

```tsx
throw new Error("Database unavailable");
```

and handled by:

```text
error.tsx
```

---

# 21. Authentication Errors

Suppose the user isn't authenticated.

You generally don't want:

```tsx
throw new Error("Unauthorized");
```

for every authentication check.

Instead, you might redirect:

```tsx
import { redirect } from "next/navigation";

export default async function Dashboard() {
  const user = await getUser();

  if (!user) {
    redirect("/login");
  }

  return <DashboardContent />;
}
```

So:

```text
No authenticated user
        ↓
redirect("/login")
```

rather than:

```text
error.tsx
```

This is an important distinction:

```text
404              → notFound()
Unexpected error → throw
Expected error   → return error state
Authentication   → redirect()
Loading           → loading.tsx
```

---

# 22. `loading.tsx` Is Not Error Handling

Consider:

```text
app/
└── products/
    ├── page.tsx
    ├── loading.tsx
    └── error.tsx
```

These serve different purposes.

### `loading.tsx`

```text
Request is still running
        ↓
loading.tsx
```

### `error.tsx`

```text
Request/rendering failed
        ↓
error.tsx
```

### `page.tsx`

```text
Request succeeded
        ↓
page.tsx
```

So the complete lifecycle can be:

```text
                 Request
                    │
          ┌─────────┼─────────┐
          │         │         │
       Loading    Success    Failure
          │         │         │
          ▼         ▼         ▼
     loading.tsx  page.tsx  error.tsx
```

# 24. A Good Production Pattern

For a production Next.js application, think in terms of this hierarchy:

```text
                    Application
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Loading         Success        Failure
          │              │              │
    loading.tsx       page.tsx       Error Boundary
                                         │
                               ┌─────────┴─────────┐
                               │                   │
                         Expected error      Unexpected error
                               │                   │
                         Return state          throw
                               │                   │
                         Show message          error.tsx
```

And for resource existence:

```text
Resource doesn't exist
        ↓
    notFound()
        ↓
not-found.tsx
```

And authentication:

```text
Not authenticated
        ↓
   redirect()
        ↓
      /login
```

# 25. The Most Important Next.js Error APIs

| Mechanism          | Purpose                         |
| ------------------ | ------------------------------- |
| `error.tsx`        | Route-level unexpected error UI |
| `global-error.tsx` | Root-level fatal error UI       |
| `not-found.tsx`    | 404/resource-not-found UI       |
| `notFound()`       | Trigger not-found handling      |
| `reset()`          | Retry the failed route segment  |
| `try/catch`        | Handle errors locally           |
| `redirect()`       | Redirect intentionally          |
| `loading.tsx`      | Loading/fallback UI             |
| `throw`            | Propagate unexpected errors     |

---

# 26. What You Should Remember

If you're learning Next.js App Router, memorize this mental model:

```text
                 NEXT.JS REQUEST
                       │
                       ▼
                  Is it loading?
                   /       \
                 YES        NO
                  │          │
                  ▼          ▼
             loading.tsx   Continue
                              │
                              ▼
                         Did it succeed?
                          /          \
                        YES           NO
                         │             │
                         ▼             ▼
                      page.tsx     Is it "not found"?
                                    /          \
                                  YES           NO
                                   │             │
                                   ▼             ▼
                              notFound()      throw
                                   │             │
                                   ▼             ▼
                              not-found.tsx   error.tsx
                                                  │
                                                  ▼
                                               reset()
                                                  │
                                                  ▼
                                             Try again
```

The biggest conceptual distinction is:

> **Don't use `error.tsx` for every problem.**

Use the appropriate mechanism:

```text
Expected business error → return error/state
Unexpected application error → throw → error.tsx
Missing resource → notFound() → not-found.tsx
Authentication problem → redirect()
Still loading → loading.tsx
Recoverable failure → reset()
```

This is the foundation of **error handling and error recovery in modern Next.js App Router**.
